# Turn FlowDesk into evidence of your own work

## Your first real project: launch a portfolio feature

Use FlowDesk to manage adding a useful feature to your own portfolio over two weeks. Choose a feature you can actually deliver, such as a project gallery, contact page or accessible mobile navigation. This is self-directed project experience.

1. **Define success.** Create a project. Write the problem, intended audience, scope boundaries, deadline and acceptance criteria. If there is no spending, use a zero budget; do not invent costs.
2. **Plan delivery.** Add 8–12 tasks covering requirements, design, implementation, testing and launch. Give each a realistic owner, date and clear completion condition. Link genuine dependencies.
3. **Inspect uncertainty.** Add at least three risks with triggers and responses: missing content, device compatibility, and scope growth are examples. Choose scores you can explain.
4. **Execute.** Complete real tasks and update the board. Record actual costs only when incurred. Keep evidence such as commit links, test notes and screenshots in task notes or your repository.
5. **Control a change.** If a new request appears, document alternatives, cost/schedule impact and your decision. If this is only a practice scenario, label it simulated. Adjust dates manually if needed.
6. **Report.** Export a status report at the end of each week. Add your interpretation: what changed, why, which decisions are needed and what happens next. Export a JSON backup too.
7. **Close.** Check each acceptance criterion against evidence. Record what worked, what missed the plan and what you would change next time.

## Evidence to keep in GitHub

Create an `evidence/` folder for your own redacted materials:

- `charter.md`: objective, scope, success criteria and constraints.
- `weekly-status-01.md` and `weekly-status-02.md`: reports with your interpretation.
- `decisions.md`: alternatives considered and reasons for decisions.
- `acceptance.md`: criterion, test, result and evidence link.
- `retrospective.md`: planned versus actual dates, lessons and next actions.
- Screenshots of your own project board, risks and completed feature.

Do not publish private project backups, contact details or confidential information. Use only genuine results; clearly label all exercises and synthetic data.

## Five-minute interview demonstration

- Explain the problem and scope in 30 seconds.
- Show the task board and explain one dependency.
- Show a risk and the action you took.
- Explain one trade-off using a change request.
- Show a status report and delivered evidence.
- Explain technical limitations: browser storage, single-user scope and no automatic scheduling.

You should be able to explain each calculation and what you personally did. The website is a tool; completing and reflecting on a real project gives you substantive examples to discuss.

## Small product improvements you can own

Pick one, open a GitHub issue with acceptance criteria, implement it with assistance if needed, then test it:

- Add a task category filter while preserving search and priority filters.
- Add a project archive workflow that keeps exported evidence.
- Add a print-friendly status report view.

Record the issue, design decision, change and test evidence. Be transparent about AI assistance and your own contribution.
